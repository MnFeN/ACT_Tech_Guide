# 同步动作与顺序执行

触发器的选项中有一个 “顺序执行” 选项（sequential）：

![image](https://github.com/user-attachments/assets/36de874a-af72-4c03-9acc-21532887a3b1)


而触发器动作也有一个 “异步执行” 选项（asynchronous）：

![image](https://github.com/user-attachments/assets/5a21b3a9-f44e-4433-8261-a5c51d213a27)

二者的行为和效果有一定的相似之处，容易引起误解，在此简要说明。

## 基本概念

每次触发器被触发时，插件需要先确定各个动作应该在什么时间执行，然后再按照这些时间安排动作。

默认情况下，一个触发器中的多个动作会在触发时一次性安排好。到了各自应该执行的时间后，默认的异步动作可以同时开始执行，因此即使它们在触发器中的编号有先后，也不能仅凭编号保证实际执行的先后顺序。

“顺序执行”和“同步执行”分别改变了这两个阶段：

- 顺序执行：改变后续动作**什么时候被安排**。
- 同步执行：改变动作到达执行时间以后，**是否必须等待前一个动作处理完毕**。

因此二者都可以用于控制动作顺序，但原理和适用场景并不相同。

## 顺序执行

顺序执行是一个触发器的属性，而非动作的属性。它改变的是动作的**安排方式**。

未额外改变任何设置的正常情况下，同一次触发中的所有动作会在触发时一次性安排好，并根据各自的延迟确定执行时间。默认动作又是异步执行的，因此几个同时到达执行时间的动作并不能保证哪个先完成。

而如果开启顺序执行，则只会先安排第一个动作。等第一个动作执行结束以后，才安排第二个动作；第二个动作结束以后，再安排第三个动作，以此类推。

因此，顺序执行可以保证同一次触发中的动作按照编号依次完成。

需要注意的是，这只保证**同一次触发内部的先后关系**。

例如：

动作 A  
动作 B  
动作 C

开启顺序执行后，一定是：

A 结束 → B 开始  
B 结束 → C 开始

但在 A 和 B 之间，完全可能有其他触发器的动作执行；同一个触发器再次触发所产生的动作，也可能穿插进来。

所以，“顺序执行”并不代表从第一个动作开始到最后一个动作结束之间，会独占整个动作执行过程。

## 同步执行

同步执行是一个触发器动作的属性。界面中的选项名称为“异步执行”，取消勾选即表示该动作同步执行。

正常情况下，动作到达执行时间后，会被允许独立执行。前一个动作刚刚开始以后，插件就可以继续开始处理后面的动作，因此多个动作可能同时进行。

如果一个动作设置为同步执行，则插件必须等这个动作执行结束以后，才能继续开始处理下一个等待执行的动作。

例如同时到达执行时间的三个同步动作：

A  
B  
C

会依次执行为：

A → B → C

只有 A 结束后才会开始 B，只有 B 结束后才会开始 C。

因此，如果一个触发器没有开启顺序执行，而其中一组没有额外延迟的动作全部设置为同步执行，那么这些动作会先按照编号一起安排好，随后再按照顺序逐个执行。

这也是一种保证动作顺序的方法。

需要注意的是，同步动作执行期间，只是**不会继续开始后面等待执行的动作**。如果此前已经有其他异步动作开始执行，那么这些动作仍然可能同时继续运行。

所以同步执行并不等于“整个插件中任何事情都停止”，也不会因为同步动作本身就冻结 ACT 的界面。

但是同步动作如果耗时很长，会使后面所有等待执行的动作都无法及时开始，因此同样应当避免让同步动作执行高耗时任务。


## 二者的差异

触发器整体设为顺序执行，或触发器中每一个动作设为同步执行，二者均可用于保证同一次触发内部的动作顺序，但实则有很大差异。

- **时间延迟**
  
  当触发器设定为顺序执行时，每个动作都会在前一个动作结束以后才开始安排。

  因此，后一个动作自身设置的延迟，是从**前一个动作结束以后**开始计算的。

  例如：

  动作 A  
  动作 B：本身执行需要 0.5 秒  
  动作 C：延迟 1 秒

  如果不开启顺序执行，那么 A、B、C 会在触发时一起安排。C 的 1 秒延迟从整个触发器触发时开始计算。

  理想情况下：

  0.0 秒：A、B 到达执行时间  
  0.5 秒：B 执行结束  
  1.0 秒：C 到达执行时间

  所以 C 大约会在 B 结束后的 0.5 秒执行。

  如果开启顺序执行，则必须等待 B 执行结束以后，才会安排 C，并从此时开始计算 C 的 1 秒延迟。

  理想情况下：

  0.0 秒：B 开始  
  0.5 秒：B 结束，并开始计算 C 的延迟  
  1.5 秒：C 到达执行时间

  所以此时 C 会在 B 结束后的约 1 秒执行。

  有些动作本身略微耗时，如获取全部实体列表、遍历大量变量，可能使后续动作产生毫秒级的推迟；

  还有些动作耗时更长，如没安装 TTS 插件时的大妈音 TTS、系统蜂鸣声，以及某些脚本的首次编译执行，都可能产生明显的推迟。

  （这也就是为什么触发器自检中会明确强调必须安装 TTS 插件，否则触发器可能出现时序问题。）

  所以，对于包含“延迟若干秒执行某操作”的触发器，如果前面包含高耗时动作且使用顺序执行，则这些耗时会累积到后续动作的执行时间上。

  对于时间敏感的触发器，例如按照战斗时间轴在固定时间播报内容，应特别注意这一点。
  
- **阻塞后续动作**

  根据前文所述，顺序执行只会使**这个触发器本次触发中的后续动作**等待前一个动作结束。

  前一个动作执行期间，其他触发器已经准备好的动作仍然可以执行。

  而同步执行的动作开始以后，在它结束之前，后面所有还在等待执行的动作都不能继续开始。

  也就是说，一个耗时很长的同步动作不仅会推迟同一个触发器中的后续动作，也可能推迟其他触发器已经准备执行的动作。

  所以切勿使用同步动作执行高耗时的任务。

  例如需要长时间等待、复杂计算、首次编译耗时明显的脚本等，一般都不适合设置为同步执行。

- **动态延迟**

  一个动作被安排时，就会立即计算它自身设置的延迟。

  这意味着，如果你写了一个根据某些条件变化的延迟，例如：

  动作 A：计算并设置变量 `t`  
  动作 B：延迟 `t` 毫秒执行

  那么是否开启顺序执行会直接影响结果。

  非顺序模式下，A 和 B 会在触发器刚刚触发时一起被安排。

  此时 A 还没有真正执行，因此 B 在计算延迟时，读取到的 `t` 仍然是 A 执行以前的值。

  即使 A 设置为同步执行也没有用，因为 B 的延迟时间早在 A 开始执行以前就已经确定。

  而顺序执行时，必须等 A 执行结束以后才会安排 B。

  所以 B 此时读取到的是 A 刚刚计算出的新 `t`，可以按照预期动态决定延迟。

  因此，需要由前面的动作计算后续动作延迟时，应使用顺序执行。

- **打断序列**
  
  如果触发器中包含“打断动作序列中此触发器（或所有触发器）的动作”之类的操作，两种模式下会有所区别。

  非顺序模式下，同一次触发中的后续动作通常在触发时就已经全部安排好了。

  因此执行打断操作时，这些尚未执行的后续动作已经存在，可以被正常取消。

  顺序执行时，后续动作要等前一个动作结束以后才会安排。

  因此，如果当前动作执行打断操作，此时后续动作还不存在，也就没有东西可以被打断。

  当前动作结束以后，顺序执行仍然会继续安排下一个动作。

  所以如果希望通过“打断动作”取消同一次触发中尚未执行的后续动作，应特别注意顺序执行的这一行为。

- **多次触发**

  副本中经常会遇到需要连续触发一个或几个触发器，获取若干份数据以后立刻继续处理的情况。例如：

  - 绝神兵三连桶获取点名推送至列表中，推送三次后立刻排序并标记。
 
  - 绝欧 P5 击退塔出现时，将塔的坐标存储至列表中，根据远近线判断触发 5 或 6 次后立刻计算向量和的角度，确定相对北的方向。
 
  - P12s 几乎同时生成 12 个多面体、8 个头顶标记、8 个 α/β debuff。我们需要获取全部多面体、自己的标记和 debuff 才可确认后续解法，共触发 8 + 1 + 1 次后才能开始后续处理。
 
  这些触发器中，通常希望一次触发开始修改数据以后，先完整完成这一次触发中的相关处理，再开始处理下一次触发。

  例如一次触发中有：

  动作 A：向列表添加数据  
  动作 B：计数 +1  
  动作 C：如果数量足够，则开始计算结果

  如果开启顺序执行，则 A 完成以后才会安排 B。

  但在 A 和 B 之间，其他触发产生的动作可能已经开始执行。

  于是就可能出现类似：

  第一次触发 A  
  第二次触发 A  
  第一次触发 B  
  第二次触发 B

  这样的穿插。

  虽然每一次触发内部仍然满足“A 在 B 前面”，但如果这些动作共同修改同一个列表、计数器或其他变量，结果就可能和预期不同。

  对于普通的连续触发场景，如果这些动作没有额外延迟，可以使用：

  **关闭顺序执行，并将这一组动作全部设为同步执行。**

  这样，一次触发时，这组动作会先按照编号全部安排好，再依次执行完毕。

  因此正常情况下会形成：

  第一次触发：A → B → C  
  第二次触发：A → B → C  
  第三次触发：A → B → C

  而不会变成：

  第一次 A → 第二次 A → 第一次 B → 第二次 B

  所以对于“连续收集数据 → 计数 → 满足次数后立即计算”这一类触发器，**非顺序 + 全同步**通常比顺序执行更适合。

  需要注意，这里的结论针对正常的触发器触发流程，并且要求这些需要连续处理的动作本身没有额外延迟。

  一旦其中某个动作设置了延迟，它本来就应该在更晚的时间执行，自然不能再认为整次触发的所有动作都会紧挨在一起。

  - **注 1：**

    还有一种写法：用一个触发器多次触发获取数据；另一个触发器单次触发，延迟一定时间后播报结果。

    但是当你可以确定预期触发的次数，且触发后需要尽早开始处理机制的情况下，**请勿使用延迟触发代替计数**。

    例如本来明确知道需要收到 8 次数据，那么在计数达到 8 时立即开始处理，通常比“第一次收到数据以后等待 500 ms，再假定数据已经收齐”可靠得多。

    后者依赖的是“这些数据通常会在规定时间内到齐”，而不是“已经确认收到了全部数据”。

    延迟较低时，可能因为网络、游戏日志或设备负载的波动，偶然出现开始处理时数据仍未收齐的情况；

    延迟设置得过高，又会无谓推迟结果，使原本可以更早得到的播报、标点或绘图延后。

    因此，如果可以明确知道应该接收多少次数据，应优先使用计数判断数据是否收齐，而不是猜测一个“应该已经收齐”的延迟时间。

  - **注 2：**

    目前请避免使用“互斥锁”功能。

    该功能在 1.1.7.x 版本中已经确认存在与同步动作组合使用时可能导致严重异常的[问题](https://github.com/paissaheavyindustries/Triggernometry/issues/102)，该问题目前仍未关闭。

    顺序执行 / 同步执行已经能够覆盖绝大多数常见的动作排序需求，所以一般没有必要再使用互斥锁。

## 补充说明：动作结束

有必要在此明确“动作结束”的含义：

有时，动作结束并不意味着这个动作要求的外部效果已经全部完成，而只是代表插件已经完成了自己需要做的工作，可以继续处理后面的动作。

举个例子，当使用 TTS 插件时，文本转语音 TTS 动作实际做的是向 TTS 插件发送一个“播报 XXXX”的请求。

请求成功发送以后，这个动作本身就已经结束，Triggernometry 可以继续处理后面的动作。

它并不会等待这一整句话真正播放完毕以后，才认为 TTS 动作结束。

因此，例如：

第一句话：播报持续约 2 秒  
第二句话：设置延迟 3 秒

如果使用顺序执行，那么“第二句话”的 3 秒延迟，是从**第一条 TTS 请求发送完成**以后开始计算，而不是从第一句话真正播放结束以后开始计算。

同样，同步执行也只会等待“发送 TTS 请求”这个动作本身完成，不会等待声音播放结束。

也就是说，无论下图所示的触发器是否为顺序执行或同步执行，“第二句话”的实际播报时间都应接近第三秒，而不是第五秒。
