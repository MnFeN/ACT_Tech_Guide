# 0649 p2 低两位：危急时刻与加时状态快照

[ActorControl 分类与参数](../README.md) · [附注索引](README.md)

0649 的 141789160 先将 manager+4D4h 低 2 位清零，再分别复制完整 p2 的 bit0／bit1，其他 p2 位不进入本字段。与已核对的 0642 增量事件串联后，可给这两位补上实际用途，而不只写未知状态 byte。

| 0649 p2 | 内容 |
| --- | --- |
| bit0 | **同一状态的增量来源**：0642 命令 7 按完整 p2==1 设置／清除 manager+4D4h.bit0<br>**已证消费者**：该位由 0 变 1 且增量 p3==1 等门控满足时尝试 ScreenImage485“危急时刻”；位已置则不重复走该首次提示。虚 3=141788F60 返回此位 |
| bit1 | **同一状态的增量来源**：0642 命令 9 按完整 p2==1 设置／清除 manager+4D4h.bit1<br>**已证消费者**：对应加时状态及首次提示去重：样式 2 提示 1107“进入加时阶段”，其它样式提示 484“不胜不休”；HUD 以该位决定加时条，阶段 22 音乐也在 909/910 之间选择 |

这里采用“危急时刻提示对应状态／去重位”和“加时状态／去重位”的客户端名称，不用旧玩法外文名称跨场景套用。ScreenImage 中文字、真实纹理和 HUD时间条已在SpectatorOvertimeAndTeamProgress.md 核对。

## 初始快照与增量参数的宽度不同

0649 是复制 bit，不把整个 p2 按==1 归一；例如 p2=0x101 仍把 bit0 置 1。0642 命令 7／9 则比较完整 DWORD 恰 1，0x101 在这些增量命令中会清相应状态位。不能因为目标字段相同就把两种线上参数的规则统一。

0649 写快照本身没有进入上述首次 ScreenImage 分支；它同步当前状态，并会影响后续 HUD／音乐／增量去重条件，不能直接写成收到 0649 就播放提示。

manager+4D4h.bit2 是成员数据刷新标记：完整成员资料 141789280 另 OR4，14178A920 在该位置位时调用 141A3E120 处理成员 vector，成功才清 4；0649 的 FC 掩码保留它。这个本地 bit2 不是 0649.p2.bit2；高于 bit1 的网络位在本初始化表达式中不读。0640 初始化曾用 F8 清低 3 位，属于另一初始化操作。

阶段 22 的加时音乐路径 141789FE0 还要求 SheetStatus==2、转区／游戏状态门控满足，bit1 置位选 910，否则 909；不表示所有状态一收到快照立即换音乐。

本补充使 0649.p2 两位用途更明确，但 p3 中间 ushort 及 p4/p5 等字段仍缺独立业务名字，类别保持待查。证据：141789160 C/ASM、141789850 命令 7/9、141788F60、141789280、141789FE0 及前述提示／HUD 专项资料。
