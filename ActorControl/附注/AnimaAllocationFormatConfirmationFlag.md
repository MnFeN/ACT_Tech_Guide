# 0398 p2.bit31：属性式样确认与重新设定门控

[ActorControl 分类与参数](../README.md) · [附注索引](README.md)

0398 把 p2 最高 bit（连续载荷 byte7.bit7）归一为 0／1，保存 Anima 模块 142AD9730+0Bh，即 142AD973B。此前以“完成相关旗标，细分待查”保留；本次补入独立事件物品使用路径与实际错误文本后，改用客户端用途名称：**属性分配方案可确认标志／旧式样重新设定提示门控**。这是行为描述，不冒充官方字段名，也不等同“分配点已经达到 180”。

## 元灵透镜的直接读取者

140890A90 是 EventItem 使用处理函数。其类型 6 分支明确区分 2001993 乌兰的笔记、2001994 元灵透镜及另一个物品；本字段在 **2001994 元灵透镜**分支读取。

已有窗口切换路径没有提前处理，且 Quest 短 ID0918（完整 67864“培育人造元灵”）已接受时，140890CFC 比较 byte142AD973B。该位非 0 直接跳过下面的式样提示检查；为 0 时遍历主手／副手各五项分配值，只要任意项非 0，就于 140890DD1 以 LogMessage1474 输出：

> 式样发生了变更，目前无法确认。请重新设定属性。

随后立即返回，不推进该分支后面的透镜界面准备。若十项全部 0，则即便此标志为 0 也不输出该提示，继续后面的准备路径。故准确条件为 `!flag && anyAllocatedValue != 0`，不能缩成 flag0 无条件禁止使用，也不能将 flag1 当作“总点数已满”。

文本与 Quest实际资源保存在resources-anima-first-allocation-flag-log.json，含原始 SeString；不是按旗标位置猜名。这里没有证明是哪次补丁改变式样、服务端如何迁移旧分配或需要哪一版本号，因此不命名为某个具体版本迁移完成位。

## 与 180 点完成流程的关系

140893880 要求此位非 0，**另加**十项分配总和>=180 才返回真。具名 Lua OpenAnimaWeapon5StatusAllocation 的 wrapper140DFCAA0 据此返回 2；Quest67864 原生脚本 JobRel300_02328 把返回 2 导向 scene6 的武器极限／找阿尔达希尔流程。总和>=180 但本位 0 不会走这项完成返回；本位 1 但总和不足 180 同样不会走。

这说明“当前分配方案可确认”的门控与“分配总点数达到要求”是两个独立条件，纠正此前将本位笼统归入完成状态的命名。脚本及原始 luasm 位于 client/scripts-anima-allocation/，原先的脚本返回／场景证据仍保留。
