# 00F3：相对角色定位、步行/跑步与到位后的双角色动作

[ActorControl 分类与参数](../README.md) · [附注索引](README.md)

**纠错：p4 低 16 位是 ActionTimeline ID，不是确认序号。** 直接消费者会将两份相同值交 TimelineContainer.PlayResolvedActionTimeline，分别作用于路由角色和仍存在的参考角色。

| 参数 | 语义 |
| --- | --- |
| p1 | 参考 BattleChara EntityId；找不到时不建立轨迹 |
| p2 | byte2=X、byte1=Y、byte0=Z，均 unsigned /10 米；最高 byte 未读 |
| p3 low16 | 相对角度(value-180)*π/180，再加参考角色朝向并规范化 |
| p3 high16 | 整体非零为步行，零为跑步；不是仅单 bit16 |
| p4 low16 | 到位后动作时间轴 ID，写自身与参考角色的两份槽 |
| p4 high16、p5..p8、独立 target | 未读 |

## 初始化与真正消费者

141820DD0 按 p1 查角色，141820A40 将偏移按参考角色的当前朝向旋转后加坐标，保存终点和最终朝向。它设置外层模式 10、子状态 9、优先级 7，内部共用轨迹记录类型 11；这些是不同层级，不能把记录 11 叫外层模式 11。

InputController 初始化 141834440 在 self+520h 建立 10 个子状态对象，这对全局 142AB28B0 恰为 142AB2DD0。14180CDC0 的索引 8 对象实际 vtable1422DCE20，虚 1=141810C50 更新、虚 2=141810E60 查询移动动画。该对象与子状态 9（一基索引）对应，不是根据相邻函数地址猜消费者。

## high16 为何可以明确叫步行

高 16 位非零时速度 2，零时 5，以水平距离/速度算持续时间，低于 0.0166 置 0。141810E60 再读取同一 walk 标志，移动阶段分别选 ActionTimeline13 或 22，经 141822990 作角色外观相关重映射。本机资源 13 的 Key=normal/walk，22=normal/run。因此“步行/跑步”有独立动画资源互证，不仅靠两个速度常数猜测。

## 逐帧及 p4 纠错

141810C50 累积输入 delta，在持续时间内对保存的起点/终点线性插值 XYZ；控制器+438h bit1 置位时 Y 保留角色当前值。朝向也在开始阶段作平滑，再采用最终朝向。参考角色坐标不用于每帧重算终点，因此不是持续跟随。

自然到位后，141810F10 设置最终坐标/朝向。随即明确读取记录+34Ch 及+34Eh 两个 ushort（本包均来自 p4 低 16 位），以它们作为第二参调用 TimelineContainer_PlayResolvedActionTimeline：一次给路由角色；参考 EntityId 仍能查到时另一次给参考角色。阶段 1 通过 1408BF680 等待双方对应时间轴不再播放才完成。它没有将 p4 送网络确认序号函数。

此前只看到两个 ushort 缓存就把 p4 命名“确认序号”，该解释已撤回；IDA 的 sequence 形参也已更正为 actionTimelineId。p4=0 等输入仍交下层时间轴解析，本入口没有额外有效行号钳制，不能补不存在的收包验证。

无本类回放样本。以收包布局、真实子状态构造/虚表、逐帧播放调用及资源共同确认，不将其绑定到某一个未证实的双人表情名称。
