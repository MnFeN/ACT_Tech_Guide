# 金碟内容准备人数：0456 及 0455 阶段切换

0456 的 p1 为已准备人数，p2 为所需准备人数，p3/p4 及额外参数未读。默认委派 140E6B110 取得 Agent170 GoldSaucerHud，通过 1410A4B10 和 1410A4B60 分别写 NumberArray81（固定 FFCS 名 RaceChocobo）[2]、[3]。

## 实际界面消费者

| 窗口 | 内容 |
| --- | --- |
| RaceChocoboReady | **更新函数**：1416D3220<br>**显示数字**：p1 / 8<br>**完成指示控件**：node5；p1>=p2 时可见 |
| LovmReady | **更新函数**：1416E6280<br>**显示数字**：p1 / p2<br>**完成指示控件**：node4；p1>=p2 时可见 |

两者调用 1416D3040(total,current,denominator)，仅 total>0 才格式化更新并判断指示控件。实际数字文本节点分别是 7 和 9。14064AFE0 将 current 与 denominator 两整数传给 Addon19，原始 SeString 为 022003E802032F022003E80303，即整数参数 1、斜杠、整数参数 2。静态 ULD 与初始化函数相互核对：陆行鸟窗口文本 9135 是“正在确认准备情况”。这证明数据为准备人数；并非赛中分数、名次或时间。比较是 signed32，没有额外证明网络输入总会被限制在正常人数范围。

六份 RaceChocobo/Lovm 的 Status、Confirm、Ready 实际 ULD 均已提取。Status 窗口只消费同数组[1]及 StringArray76，Confirm 窗口主要消费[0]/[1]和字符串；不能把同数组相邻字段直接套成 0456 的含义。LovmReady 共用数组名 RaceChocobo 是原生复用，不代表只处理陆行鸟。

## 与 0455 的关系及尚未完成部分

0455 的 p1 是界面阶段：0 隐藏，1 清理对话并准备正文，2 建立确认窗口，3 建立 Ready 窗口，4 关闭 Ready 窗口。p1=7 另行标记模式 2，将数组[2]=1、[3]=2，按 p2 非零保存子模式，并把传给 HUD 的阶段转成 1。p1=2 缓存 p2 绝对截止秒数到该委派对象+68h，详见后节。5/6 等值后续已核对为保存及通用非零资格路径，无独立专用窗口动作；宽度与完整读取审计见 GoldHudPhaseFallbackAndWidth.md。

Agent 模式 byte+72 为 0 走 RaceChocobo、1 及 2 走 Lovm 布局。模式 2 正文 Addon9528/9549 明确为“幻卡对局室内匹配：通常对局／大赛对局”，说明共用 HUD 还用于幻卡匹配，不能将 Agent 整体名称局限为萌宠或赛鸟。

静态 EXE、固定 FFCS 及本机资源交叉核对；当前 408 回放中 0455/0456 无样本，未做动态游戏观测。原生函数 C/ASM 与 ULD、字符串引用、虚表快照均位于 client 目录；资源为 resources-gold-hud-ready*.json。

## 0455 阶段 2 的 p2：绝对截止秒数

140E6B110 把 p2 存入 handler+68h；传给 140E6A7C0 的是 handler+30h，因此该助手读取自身+14h 正好是同一字段。阶段恰为 2 时，助手取 GetServerTime 低 32 位，与截止值作 uint32 比较：当前时间>=截止则剩余 0，否则截止减当前。1410A4A30 把剩余秒写 NumberArray81[1]，并格式化进 StringArray76[0]；确认窗口与状态窗口读取此文本。140E6AF80 每次更新继续刷新，不靠本地浮点倒计时。另一个消费者 140E6A480 使用同一 20h 子结构，也有相同语义。

阶段 7 的 p2 布尔含义已由 Addon9528/9549 证实为通常／大赛幻卡匹配选择。此前“阶段 2 缓存数值”以及“阶段 7 结算相关布尔”的笼统表述已修正。离开阶段 2 的 1410A5530 清理的是该阶段播放界面音效 74 所保留的两个句柄（虚调用+288、参数 500），没有清截止值，也没有证据指其为停止比赛计时。


[阶段默认分支与宽度补证](GoldHudPhaseFallbackAndWidth.md) 已补全部 9 个 getter 调用点及 Agent 直接字段读者；不为没有专用分支的值编造服务器名称。
